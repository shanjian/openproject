# Admin-shareable invitation & password-reset links

Date: 2026-08-10

## Problem

Today, both the "invite a new user" flow and the "forgot password" flow deliver
their one-time token as a URL embedded in an email — there is no way to get
that URL without email delivery. Admins who want to onboard a user or reset a
password via a secure chat app (Slack, Teams, Signal, etc.) instead of email
currently have no supported way to do so.

## Goal

Give admins a way to generate the same kind of token-bearing URL that the
mailer already builds, and copy it to the clipboard directly — without
necessarily sending an email.

## Non-goals

- The self-service "forgot password" flow (`account/lost_password`, no admin
  involved) is untouched — it remains email-only, exactly as today.
- No new UI for entering/typing a password on the admin's behalf — the
  existing "set a password directly as admin" flow in `UsersController#update`
  is untouched.
- No change to token *consumption* logic (`AccountController#activate` /
  `#lost_password`) beyond the one guard fix described below — a link
  generated by an admin is consumed through the exact same code path as one
  generated by email.

## Flow 1 — Invitation link

- New button **"Copy invitation link"**, rendered next to the existing "Send
  invitation" button in `app/components/users/edit_page_header_component.html.erb`
  and `show_page_header_component.html.erb`. Same visibility guard as today's
  button (`@current_user.allowed_globally?(:create_user) && @current_user.id != @user.id`).
- New route `POST /users/:id/invitation_link` → `UsersController#invitation_link`.
- Implementation: calls `UserInvitation.reinvite_user(@user.id, send_notification: false)`.
  `UserInvitation.reinvite_user` gains a `send_notification: true` keyword
  argument (default preserves the existing "Send invitation" button's
  behavior, which calls it with no argument).
- The action builds the URL the same way `UserMailer#user_signed_up` does
  (`url_for(controller: "/account", action: :activate, token: token.value)`),
  then redirects back to the user edit page with the URL delivered via flash
  (see "Clipboard delivery" below).

## Flow 2 — Admin-issued password-reset link

- New button **"Copy password reset link"**, shown only when
  `@user.active? && @user.change_password_allowed?` (this already excludes
  LDAP/SSO-only accounts and instances with `disable_password_login?` set —
  see `User#change_password_allowed?`).
- New route `POST /users/:id/password_reset_link` → `UsersController#password_reset_link`.
- Implementation: creates `Token::Recovery.create!(user_id: @user.id, data: { channel: Token::Recovery::CHANNEL_CHAT_LINK })`
  — the same call `AccountController#lost_password` makes for the self-service
  flow, just without invoking `UserMailer.password_lost`. The `data.channel`
  marker controls the token's validity (see "Token validity" below).
- The resulting URL points at the *existing* `account/lost_password?token=...`
  action — no new consumption code. Whoever opens the link lands on the same
  "choose a new password" page a self-service reset would show.

## Clipboard delivery (both flows)

The generating action redirects back to the user edit page with the
generated URL stashed in a dedicated flash key (e.g. `flash[:copyable_link]`)
alongside a plain confirmation message. A small Stimulus controller on the
flash partial reads that value on `connect()` and calls
`navigator.clipboard.writeText(url)`. The flash message itself also renders
the raw URL as text, so if the clipboard write is blocked (permissions,
non-HTTPS dev environment, etc.) the admin can still select and copy it
manually — the JS copy is a convenience, not the only path to the link.

## Token validity

Two different validity periods are needed for `Token::Recovery`, depending on
how the token was delivered:

- **Email (self-service "forgot password")** — bumped from the current 1 day
  to a fixed constant `Token::Recovery::EMAIL_VALIDITY = 3.days`. An emailed
  link may sit unread in an inbox longer than a chat message would.
- **Chat link (admin-generated via Flow 2)** — stays at
  `Token::Recovery::CHAT_LINK_VALIDITY = 1.day`.

`Token::Recovery` currently exposes a class-level `validity_time`
(`ExpirableToken` delegates the instance method to `self.class`). To vary
this per-instance without a schema change, `Token::Recovery` overrides the
instance method to read a marker out of the existing `data` column
(`Token::Base` already serializes `data` as a hash):

```ruby
module Token
  class Recovery < Base
    include ExpirableToken

    CHANNEL_CHAT_LINK = "chat_link"
    EMAIL_VALIDITY = 3.days
    CHAT_LINK_VALIDITY = 1.day

    def self.validity_time
      EMAIL_VALIDITY
    end

    def validity_time
      data&.fetch("channel", nil) == CHANNEL_CHAT_LINK ? CHAT_LINK_VALIDITY : self.class.validity_time
    end
  end
end
```

`data` is set via mass-assignment on `.create!`, so it's present before the
`after_initialize :set_expiration_time` callback computes `expires_on` — no
ordering issue.

## Guard fix required in `AccountController#lost_password`

The action currently gates its *entire* body — including consuming an
already-issued token — behind `Setting.lost_password?`:

```ruby
def lost_password
  return redirect_to(home_url, status: :see_other) unless allow_lost_password_recovery?
  ...
```

If an instance turns off self-service lost-password recovery, an
admin-issued link would silently redirect home instead of working. Per your
call, that setting should only gate the *self-service request* path, not
token consumption. The fix splits the guard:

```ruby
def lost_password
  return redirect_to(home_url, status: :see_other) if OpenProject::Configuration.disable_password_login?

  if params[:token]
    # token consumption — reachable regardless of Setting.lost_password?
    ...
  else
    return redirect_to(home_url, status: :see_other) unless Setting.lost_password?
    # existing self-service GET (show request form) / POST (send email) behavior
    ...
  end
end
```

`disable_password_login?` still blocks everything, since that setting means
password auth is off system-wide — a reset link would be pointless.

## Permissions

`config/initializers/permissions.rb`:

- Add `invitation_link` to the `users:` action list under the `create_user`
  permission (alongside `resend_invitation`).
- Add `password_reset_link` to the `users:` action list under the
  `manage_user` permission (alongside `edit`, `update`).
